# Competition Console Architecture and Audit

## Objective

Portfolio OS now treats the product as a controlled head-to-head experiment:

- **Bot:** deterministic EventTraderV4 strategy engine.
- **Agent:** paid model-backed trader, initially routed through OpenRouter.
- **Winner:** the competitor with higher **net equity after attributable operating cost**, provided both books are fresh, comparable, and correctly marked.
- **Safety boundary:** paper and guarded execution remain the default. A visually impressive dashboard must never turn incomplete accounting into a winner.

## Current-state audit

The repository already contains strong trading infrastructure: Coinbase execution code, strategy ranking, backtests, reconciliation, state corruption gates, strategy kill/rehabilitation, agent-cost ledgers, budget approvals, audit records, and system-health publishing.

The product layer was fragmented across two primary front ends:

1. `apps/web/src/*`, a workflow-oriented Node operator console.
2. `trading_system/ui/dashboard.html`, a market-terminal-oriented Python dashboard.

Neither made the bot-versus-agent economics the primary object. The race was generated by `scripts/competition_scoreboard.py`, but the snapshot was not exposed through the canonical API or operator console.

## P0 defects found

### Bot realized P&L was double counted

The old scoreboard calculated bot equity as:

```text
paper_cash + paper_realized_pnl
```

EventTraderV4's accounting contract already reflects realized P&L in `paper_cash`. Its canonical paper equity is cash plus marked unrealized P&L. The old formula therefore distorted the competition.

### Open positions could be ranked without live marks

A score based on stale entry prices is not a reliable equity comparison. The new snapshot reports the missing marks and blocks the ranking instead of silently substituting a winner.

### Paid-agent cost was not part of the winner calculation

Agent research/model spend existed in the operator ledger, but the competition leader was based on raw equity. The new contract deducts attributable API and compute cost before ranking.

### System Truth contract drift

Tests and the `systemTruth.mjs` module expected `/api/system-truth`, but `server.p1.mjs` no longer routed it and the current UI no longer exposed the required fields. This broke the source-labelled health contract.

### Build entry point drift

`package.json` and `apps/web/package.json` referenced `scripts/build-web.mjs`, while the validator only existed under `archive/scripts`. The active build path was broken.

### Runtime data is still tracked

The latest `main` commit consists primarily of generated runtime JSON and state-backup churn, including a nested `portfolio-management/data/operator-state.json`. `.gitignore` contains the right patterns, but already-tracked files remain tracked. A dedicated cleanup should remove them from the index with `git rm --cached` while retaining local runtime files.

### Agent leverage accounting requires a dedicated repair

The direct-price long path in `scripts/hermes_agent_trader.py` derives base size from leveraged exposure and then multiplies P&L by leverage again on close. The add-to-position path has the same risk. This can create leverage-squared paper results and invalidates historical agent comparisons. Until repaired and replayed, the competition should be treated as experimental and ranking should fail closed when accounting provenance is uncertain.

## New API contracts

### `GET /api/competition`

Returns:

- source freshness
- bot and agent gross/net equity
- attributable paid-agent cost
- gross and net P&L/return
- drawdown, win rate, and trade counts
- cost coverage and break-even gap
- ranking validity and warnings
- explicit accounting formulas

### `GET /api/system-truth`

Restored to the P1 API and surfaced in the console.

## Competition rules

A ranking is valid only when:

1. Both books are fresh.
2. Starting capital is equal.
3. Both net-equity values are finite.
4. Open bot positions have current marks.
5. The competition snapshot is fresh.
6. Agent operating cost is deducted.
7. No ledger-integrity blocker is active.

The ranking basis is:

```text
agent_net_equity = agent_gross_equity - attributable_model_and_compute_cost
bot_net_equity   = canonical_bot_paper_equity
leader           = max(agent_net_equity, bot_net_equity)
```

## UI information architecture

The consolidated console is organized around operator decisions:

- **Overview:** race status, both books, cost coverage, warnings, and work queue.
- **Race:** authoritative side-by-side scorecard and accounting contract.
- **Trades:** normalized execution ledger.
- **Signals:** source, confidence, gross EV, model cost, and net EV.
- **Learning:** promotion requirements and currently missing lineage evidence.
- **Agent Costs:** budget, spend, cost per opportunity, and approvals.
- **Risk:** drawdown, positions, execution posture, and validity blockers.
- **System:** source-labelled System Truth.

## Next implementation sequence

1. Repair and version the agent paper-accounting model; replay/reset contaminated history.
2. Make `competition_state.json` publication part of the supervised runtime after every ledger mutation.
3. Add durable lineage: model request → signal → trade → outcome → learning proposal → challenger result → promotion/rollback.
4. Attribute every OpenRouter request to a decision, opportunity, and resulting trade cohort.
5. Add walk-forward challenger evaluation and risk-adjusted promotion gates.
6. Consolidate or retire the legacy Python dashboard after endpoint parity is proven.
7. Remove tracked runtime artifacts and add a CI check that rejects generated state files.
8. Add browser-level end-to-end tests against the deployed console.
